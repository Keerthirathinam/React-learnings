Step 0 — .npmrc
Project npm registry override

What it is: A config file that tells npm where to download packages from.

Why you need it: Corporate laptops have global ~/.npmrc pointing to AWS CodeArtifact. Personal projects need public npm. Project-level .npmrc overrides global for THIS folder only — work projects unchanged.

🏠 Analogy: Global .npmrc is your company's approved supplier list. Project .npmrc says "for this recipe, shop at the public grocery store instead."

Paste this into invoice-dashboard/.npmrc:

registry=https://registry.npmjs.org/

Symptom if missing: ERESOLVE, graphql@undefined even with correct versions.

Auto — node_modules/ (folder, created by npm install)
Installed packages — never edit, never commit

What it is: Folder created automatically when you run npm install. Can contain 100,000+ files.

What it does: Stores every package from package.json plus all their sub-dependencies. When you import React from 'react', Node resolves it to a file inside node_modules/react/.

🏠 Analogy: Your pantry. package.json is the shopping list; node_modules is everything you bought. You cook from the pantry, not the list.

Why you need it: Without it, imports fail — nothing can run.

⚠️ Never commit to Git. Listed in .gitignore. Teammates recreate it with npm install.

Auto — package-lock.json (created by npm install)
Exact version lockfile — commit this to Git

What it is: Auto-generated file recording the EXACT version of every installed package.

Why it exists: package.json says "react": "^18.3.1" (any 18.x). package-lock.json pins 18.3.1 exactly so everyone on the team gets identical installs.

🏠 Analogy: package.json says "buy milk". package-lock.json says "buy Organic Valley 2% milk, 1 gallon, lot #4821" — exact reproducibility.

Do commit this to Git (unlike node_modules). Ensures CI and teammates get same versions.

Step B — tsconfig.json
TypeScript compiler configuration

What it is: Rules file for the TypeScript compiler. Webpack's ts-loader reads this when converting .tsx → .js.

Why you need it: Browsers can't run TypeScript. ts-loader uses these rules to transform your code. Also gives you IDE autocomplete and error highlighting.

🏠 Analogy: A spell-checker rulebook — catches typos, wrong types, and missing props BEFORE the app runs.

Create file invoice-dashboard/tsconfig.json:

{
  "compilerOptions": {
    "target": "ES2020",
    "lib": ["DOM", "DOM.Iterable", "ES2020"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "strict": true,
    "skipLibCheck": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "isolatedModules": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true
  },
  "include": ["src"],
  "exclude": ["node_modules", "dist"]
}

Line-by-line — key options:

  • target: ES2020 — Output modern JavaScript browsers understand
  • jsx: react-jsx — Understand JSX; no import React needed in every file
  • strict: true — Strictest type checking; catches null/undefined bugs
  • moduleResolution: bundler — Works with Webpack's module system
  • include: [src] — Only type-check files inside src/
  • exclude — Skip node_modules and dist (not your code)
  • noUnusedLocals — Error on unused variables (cleaner code)
Step C — webpack.config.js
Bundler config — THE most important file for interviews

What it is: Instructions for Webpack — how to transform and bundle your source into browser-ready files.

Why browsers need this: Browsers only understand HTML, CSS, JS. They CANNOT run TypeScript, JSX, or hundreds of npm imports directly.

🏠 Analogy: Factory assembly line. Raw TSX files in → loaders transform → finished dist/main.js out.

Create file invoice-dashboard/webpack.config.js:

const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  entry: './src/index.tsx',

  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'js/[name].js',
    clean: true,
    publicPath: '/',
  },

  resolve: {
    extensions: ['.tsx', '.ts', '.js'],
  },

  module: {
    rules: [
      { test: /\.tsx?$/, use: 'ts-loader', exclude: /node_modules/ },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    ],
  },

  plugins: [
    new HtmlWebpackPlugin({ template: './public/index.html' }),
  ],

  devServer: {
    port: 3000,
    hot: true,
    open: true,
    historyApiFallback: true,
  },

  devtool: 'eval-source-map',
};

Section-by-section explained:

  • entry — Where bundling starts. Webpack follows all imports from here.
  • output.path — Bundled files go to dist/ folder
  • output.filename — Name pattern for output JS files
  • output.clean — Delete old dist/ contents before each build
  • resolve.extensions — Import without writing .tsx extension
  • rules[0] ts-loader — Converts .ts/.tsx files to JavaScript
  • rules[1] css-loader — Handles CSS file imports
  • HtmlWebpackPlugin — Auto-injects <script src="main.js"> into index.html
  • devServer.port — Runs at localhost:3000
  • devServer.hot — Hot Module Replacement (changes without full reload)
  • historyApiFallback — SPA routing fix; /dashboard won't 404 on refresh (Phase 5)
  • devtool — Source maps for debugging in browser DevTools

HTML shell — the ONLY HTML page in a Single Page App

What it is: Minimal HTML template. In a React SPA, the browser loads this ONE file and never navigates to new HTML pages.

Why you need it: Browsers need HTML to start. React needs a DOM element to mount into. This provides both.

🏠 Analogy: Empty picture frame. React paints the entire app inside #root. Login → Dashboard changes the painting, not the frame.

Create file invoice-dashboard/public/index.html:

<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />

What happens step-by-step when you run npm start:

  1. npm reads "start" script from package.json
  2. Runs webpack serve --mode development --open
  3. Webpack reads webpack.config.js
  4. Starts at entry: src/index.tsx, follows all imports
  5. ts-loader converts TypeScript/JSX → JavaScript
  6. HtmlWebpackPlugin injects <script> tag into index.html
  7. webpack-dev-server serves files from memory at port 3000
  8. Browser opens automatically, loads HTML → runs JS
  9. index.tsx finds #root → renders <App /> → you see Hello message

About dist/ folder: Created when you run npm run build (not npm start). Contains minified production bundles. Never edit manually. Phase 7 covers this.

Key concepts to understand

  • npm — package manager; package.json lists dependencies
  • node_modules — where installed packages live (never commit this)
  • devDependencies — tools used only during development (webpack, eslint)
  • dependencies — libraries your app needs at runtime (react, mui)
  • package-lock.json — exact version lock; commit to Git for reproducible installs

What is the difference between dependencies and devDependencies?

Answer: dependencies are packages your app needs at runtime in production — React, MUI, Apollo. devDependencies are tools used only during development — Webpack, TypeScript, ESLint. When someone runs npm install --production, only dependencies are installed. This keeps production deployments lean.

Why do we use TypeScript instead of plain JavaScript in enterprise apps?

Answer: TypeScript adds static typing — catches bugs at compile time (wrong prop types, null references) before they reach production. It improves IDE autocomplete, makes refactoring safer across large codebases, and serves as living documentation through interfaces. Enterprise teams with 50+ developers rely on this to prevent integration errors.

What does npm init -y do?

Answer: Creates a package.json file with default values (-y skips interactive prompts). It initializes your project as an npm package — giving it a name, version, and empty scripts/dependencies sections. It's always the first step before installing any packages.

What is a bundler and why do we need one?

Answer: A bundler (Webpack, Vite, Rollup) takes many source files and npm packages and combines them into files browsers can run. Browsers can't natively run TypeScript, JSX, or hundreds of separate import statements efficiently. The bundler transforms, resolves dependencies, optimizes, and outputs a few JS/CSS files.

What's the difference between Webpack and Vite?

Answer: Webpack bundles everything before serving — slower cold start but highly configurable; industry standard for complex apps. Vite uses native ES modules in dev for instant startup, then Rollup for production — faster dev experience, simpler config. Webpack is better when you need fine-grained control (custom loaders, complex splitChunks). Vite is better for greenfield projects prioritizing dev speed.

Explain the role of index.tsx vs App.tsx.

Answer: index.tsx is the bootstrap file — finds the DOM root element and mounts React. It wires providers (Apollo, Theme, Router) but contains no UI logic. App.tsx is the root React component — defines routes, layout, and app structure. Separation keeps entry/wiring concerns separate from application logic.

Why do we put HTML in public/ and React code in src/?

Answer: public/ holds static assets that don't need processing — HTML template, favicon, robots.txt. src/ holds source code that goes through the build pipeline (TypeScript compilation, bundling). This separation is a universal convention — build tools know to process src/ and copy/serve public/ as-is.

What happens when you run npm start step by step?

Answer: 1) npm reads the start script from package.json → runs webpack serve. 2) Webpack reads webpack.config.js, starts at entry (index.tsx). 3) Follows all imports, ts-loader converts TSX→JS. 4) HtmlWebpackPlugin injects script tag into index.html. 5) webpack-dev-server serves files at localhost:3000 with hot reload. 6) Browser loads HTML → executes JS → React renders into #root.

Step 1 — Replace entire webpack.config.js
Production-ready bundler config

What changes from Phase 0: Adds splitChunks, contenthash, MiniCssExtractPlugin, runtimeChunk, tree shaking flags.

Paste this entire file (replaces Phase 0 version):

const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');

const isProduction =
  process.env.NODE_ENV === 'production' || process.argv.includes('--mode=production');

module.exports = {
  entry: './src/index.tsx',

  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: isProduction ? 'js/[name].[contenthash:8].js' : 'js/[name].js',
    chunkFilename: isProduction ? 'js/[name].[contenthash:8].chunk.js' : 'js/[name].chunk.js',
    clean: true,
    publicPath: '/',
  },

  resolve: {
    extensions: ['.tsx', '.ts', '.js'],
  },

  module: {
    rules: [
      { test: /\.tsx?$/, use: 'ts-loader', exclude: /node_modules/ },
      {
        test: /\.css$/,
        use: [
          isProduction ? MiniCssExtractPlugin.loader : 'style-loader',
          'css-loader',
        ],
      },
    ],
  },

  plugins: [
    new HtmlWebpackPlugin({ template: './public/index.html' }),
    ...(isProduction
      ? [new MiniCssExtractPlugin({ filename: 'css/[name].[contenthash:8].css' })]
      : []),
  ],

  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all',
        },
        mui: {
          test: /[\\/]node_modules[\\/]@mui[\\/]/,
          name: 'mui',
          chunks: 'all',
        },
      },
    },
    runtimeChunk: 'single',
    usedExports: true,
  },

  devServer: {
    port: 3000,
    hot: true,
    open: true,
    historyApiFallback: true,
  },

  devtool: isProduction ? 'source-map' : 'eval-source-map',

  performance: {
    hints: isProduction ? 'warning' : false,
    maxEntrypointSize: 512000,
    maxAssetSize: 512000,
  },
};
Step 2 — Understand each NEW section

isProduction flag

Detects dev vs prod. npm start → development. npm run build → production. Different optimizations per mode.

output.filename + contenthash

Production: main.a3f2b1c8.js. Hash changes when file content changes → browser fetches new file (cache busting). Interview: "Ensures users get latest code after deploy."

chunkFilename

Same hash pattern for split chunks (vendors, mui, lazy-loaded routes later).

CSS: style-loader vs MiniCssExtractPlugin

  • Dev → style-loader injects CSS via JS (enables hot reload)
  • Prod → MiniCssExtractPlugin writes separate .css files (better caching)

optimization.splitChunks — interview gold

  • vendor group → all node_modules → vendors.js
  • mui group → @mui packages → mui.js (large, cache separately)
  • main.js → only YOUR code (small, changes often)
🏠 Analogy: Instead of one heavy suitcase, pack clothes (main), tools (vendors), and shoes (mui) in separate bags — only repack what changed.

runtimeChunk: 'single'

Webpack runtime in its own file. When app code changes, runtime file stays cached.

usedExports: true

Marks unused exports for tree shaking (works with mode: production).

performance.hints

Warns if bundles exceed 512KB in production — helps catch bundle bloat.

Explain the Webpack build pipeline from entry to output.

Answer: Webpack starts at the entry file and builds a dependency graph by following every import. Each file passes through loaders (ts-loader for TSX, css-loader for CSS) that transform it. plugins perform extra tasks like injecting JS into HTML. Finally, everything is bundled into output files in dist/. In production mode, it also minifies and tree-shakes.

What is a loader vs a plugin in Webpack?

Answer: Loaders transform individual files as they're imported — ts-loader converts .tsx to .js, css-loader handles CSS. They operate file-by-file during the module graph build. Plugins operate on the entire bundle — HtmlWebpackPlugin generates the final HTML, MiniCssExtractPlugin extracts CSS into separate files. Rule of thumb: loaders = file transformers, plugins = bundle-level tasks.

What is code splitting and how does Webpack achieve it?

Answer: Code splitting breaks your bundle into smaller chunks loaded on demand, reducing initial page load time. Webpack achieves this via: 1) Dynamic import() syntax — creates async chunks. 2) optimization.splitChunks — automatically separates vendor code (node_modules) into its own chunk. 3) React.lazy() — loads route components only when visited. Result: main.js is smaller; page-specific code loads when needed.

What is tree shaking? When does it work?

Answer: Tree shaking eliminates unused exports from the final bundle. It works when: 1) Using ES modules (import/export), NOT CommonJS (require). 2) Webpack mode: 'production' is set. 3) Side-effect-free modules ("sideEffects": false in package.json). Example: if you import only Button from MUI but not Table, Table code is removed from the bundle.

What does [contenthash] in output filename do and why?

Answer: [contenthash] generates a unique hash based on file content — e.g. main.a3f2b1c8.js. When code changes, the hash changes, forcing browsers to download the new file instead of using a cached old version. When code hasn't changed, the hash stays the same, so browsers use the cached copy. This is called cache busting — critical for production deployments.

What is the difference between style-loader and MiniCssExtractPlugin?

Answer: style-loader injects CSS into the DOM via <style> tags at runtime — used in development for hot reload. MiniCssExtractPlugin extracts CSS into separate .css files — used in production for better caching (browser caches CSS independently from JS) and avoids flash-of-unstyled-content. Dev = style-loader; Production = MiniCssExtractPlugin.

How does webpack-dev-server differ from a production build?

Answer: Dev server serves files from memory (not disk), enables Hot Module Replacement (HMR — changes appear without full page reload), skips minification for faster builds, and uses eval-source-map for debugging. Production build writes optimized files to dist/, minifies code, tree-shakes, splits chunks, and generates source maps. Dev prioritizes speed; production prioritizes performance and size.

What is historyApiFallback and why do SPAs need it?

Answer: In a SPA, React Router handles routing client-side — URLs like /dashboard don't correspond to actual files on the server. Without historyApiFallback, refreshing /dashboard would return a 404 from the dev server. This option tells the dev server: "for any unknown URL, serve index.html instead" — letting React Router take over. Required for all client-side routed apps.

How do you structure a large React application?

Answer: Feature-based or layer-based structure: pages/ (route-level components), components/ (reusable UI), hooks/ (shared logic), types/ (TypeScript interfaces), graphql/ or api/ (data layer), theme/ (styling). Pages compose components; components stay dumb and reusable; hooks extract logic. This scales because teams can own features without stepping on each other.

What is the difference between a page component and a presentational component?

Answer: Page (container/smart): tied to a route, fetches data (useQuery), manages state, passes data down. Presentational (dumb): receives props, renders UI, no API calls — e.g. InvoiceTable receives invoices array as prop. This separation makes presentational components reusable and easy to test in Storybook without mocking APIs.

What are TypeScript interfaces vs types? When use each?

Answer: Both define shapes. interface can be extended/merged (declaration merging) — good for object shapes and public APIs. type can represent unions, primitives, tuples — e.g. type Status = 'PAID' | 'PENDING'. Convention: use interface for object props/models, type for unions and utility types. Functionally similar for most cases.

What is React 18's createRoot and why replaced ReactDOM.render?

Answer: createRoot enables React 18's concurrent features — automatic batching, transitions, Suspense improvements. Old ReactDOM.render() was synchronous and is deprecated. New API: createRoot(container).render(<App />). Concurrent mode lets React interrupt low-priority renders for better UX (e.g. keep input responsive while heavy list renders).

Explain props vs state. When to lift state up?

Answer: Props — data passed from parent to child, read-only in child. State — data owned and managed by a component, changes trigger re-render. Lift state up when two sibling components need the same data — move state to their closest common parent and pass down via props. Example: search term in InvoiceListPage passed to both FilterBar and InvoiceTable.

What are custom hooks and why extract logic into them?

Answer: Custom hooks (functions starting with use) encapsulate reusable stateful logic — e.g. useAuth(), useThemeMode(). They let you share logic between components without duplicating code or using HOCs/render props. Rules: can call other hooks, must follow Rules of Hooks. Keeps components focused on rendering.

What is the virtual DOM and how does React's reconciliation work?

Answer: Virtual DOM is an in-memory JavaScript representation of the real DOM. On state change, React creates a new virtual DOM tree, diffs it against the previous tree (reconciliation), and updates only the changed nodes in the real DOM. This is faster than manipulating the DOM directly for every change. React 18's Fiber architecture allows interruptible rendering for better performance.

export const resolvers = {
  Query: {
    dashboardStats: () => {
      const paid = mockInvoices.filter((i) => i.status === 'PAID');
      const pending = mockInvoices.filter((i) => i.status === 'PENDING');

        totalInvoices: mockInvoices.length,
        totalRevenue: paid.reduce((sum, i) => sum + i.amount, 0),
        pendingAmount: pending.reduce((sum, i) => sum + i.amount, 0),
        overdueCount: overdue.length,

Try answering aloud first, then click to check.

What problem does GraphQL solve that REST doesn't?

Answer: REST returns fixed data shapes per endpoint — often over-fetching (too much data) or under-fetching (need multiple requests). GraphQL lets the client request exactly the fields it needs in one query. One request for invoices with nested payments vs three REST calls. Also: strongly typed schema serves as a contract between frontend and backend teams.

Explain query vs mutation vs subscription.

Answer: Query — read data (like GET), e.g. fetch invoices. Mutation — write/change data (like POST/PUT/DELETE), e.g. login, create invoice. Subscription — real-time updates over WebSocket, e.g. live payment notifications. Queries are cacheable; mutations invalidate/update cache; subscriptions push data continuously.

What is the Apollo Client cache and how does it work?

Answer: Apollo Client normalizes API responses into a flat, in-memory cache keyed by type+ID. When you query the same invoice twice, the second call returns cached data instantly (no network request). Mutations can update the cache directly. fetchPolicy controls behavior: cache-first (default), network-only, cache-and-network. Dramatically reduces unnecessary API calls in dashboards.

What is the N+1 problem in GraphQL?

Answer: When fetching a list of N items, the resolver makes 1 query for the list + N individual queries for related data — e.g. 1 query for 100 invoices + 100 queries for each invoice's payments = 101 DB calls. Solutions: DataLoader (batch requests), join queries at DB level, or Hasura-style relationship resolution. A common backend performance issue interviewers test for.

How do you handle loading and error states with useQuery?

Answer: const { data, loading, error } = useQuery(GET_INVOICES). Show skeleton/spinner when loading is true. Show error message/retry button when error exists. Render data when loaded. Never show blank screen during loading — use MUI Skeleton components matching the final layout shape for better perceived performance.

What is a GraphQL schema? Who defines it?

Answer: The schema is the typed contract defining all types, queries, mutations, and subscriptions available in the API. Written in Schema Definition Language (SDL). Usually defined by the backend team (or auto-generated by Hasura from a database). Frontend teams use it to write queries and can generate TypeScript types from it via GraphQL Codegen.

What is fetchPolicy in Apollo and when would you change it?

Answer: Controls how Apollo interacts with cache vs network. cache-first — check cache, fetch if missing (default). network-only — always fetch, ignore cache (fresh data on every visit). cache-and-network — return cache immediately, also fetch fresh data (good for dashboards). Use network-only for payment data; cache-first for static reference data.

How is GraphQL typed with TypeScript (codegen)?

Answer: GraphQL Code Generator reads your schema + query files and auto-generates TypeScript types for queries, mutations, and variables. Example: useQuery<GetInvoicesQuery, GetInvoicesQueryVariables>. Eliminates manual type definitions, catches mismatches between frontend queries and backend schema at compile time. Run as part of CI pipeline when schema changes.

What is an Error Boundary and what errors does it NOT catch?

What is WCAG and what are the key accessibility principles?

Answer: Web Content Accessibility Guidelines — international standard for accessible web content. How do you make a React app keyboard navigable?

What ARIA attributes do you know and when to use them?

What is focus management and why is it important in modals?

How do you design a component API (props interface)?

How do you implement focus trap in a Modal?

What is Gulp and how does it differ from Webpack?

Answer: Gulp is a task runner — automates file transformation tasks (SCSS→CSS, minify, compress images) using code-over-config pipelines. What is a Gulp stream/pipeline?

What is the difference between Gulp watch and Webpack dev server HMR?

Webpack HMR (Hot Module Replacement) updates only the changed module in the browser without full reload — preserves app state. HMR is faster and better UX for JS/React. Gulp watch is simpler and fine for CSS/asset tasks where full recompile is fast.

When would you use Gulp vs Webpack vs both together?

Answer: Webpack alone — modern React/TS apps (handles JS, CSS via loaders). Gulp alone — simple static sites, asset-heavy pipelines (images, fonts, SCSS).
